## What I did not manage
All 39 of 39 checks passed cleanly on the automated test suite and all rubric deliverables have been fully achieved. A technical limitation of our automated canary gate implementation is that it evaluates health solely via HTTP 5xx error counts and error rates reported by the router. Consequently, the gate would not automatically detect silent semantic regressions (where endpoints respond with HTTP 200 OK but return malformed or incorrect JSON payloads) or subtle p99 latency regressions that do not trigger the router's 10-second timeout. Detecting such issues in production would require synthetic semantic contract assertions and APM latency percentile monitoring.

## What I would do differently
1. **Pre-provision Target Host Infrastructure:** I would verify and pre-install the target Node.js runtime ($\ge 22.13$) and Docker Compose V2 on the deployment VM before initiating test runs, avoiding initial test interruptions caused by system package discrepancies (`node:sqlite` absence in Node 18).
2. **Automate Version Build Arguments in Package Scripts:** I would encapsulate image builds into standardized npm commands (e.g., `npm run build:v2` passing `--build-arg APP_VERSION=2.0.0`) to avoid human oversight where an omitted build argument causes the container's `/version` endpoint to report default version metadata.
3. **Automate Contract Probing on API Headers:** I would add automated pre-flight curls verifying authentication headers (such as `x-admin-token` vs `Authorization: Bearer`) against `src/app.js` before starting long continuous load runs.
